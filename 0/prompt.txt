de plsu les tests devrait etre écrits comme si c'etait une docuemnattion vivante:
Dire que **les tests doivent être écrits comme une documentation vivante**, c’est attendre d’eux qu’ils permettent à quelqu’un de comprendre **ce que le logiciel est censé faire**, en lisant des exemples concrets que l’on peut exécuter.

Par exemple, sur une Website Factory, un Tech Lead qui découvre le projet devrait pouvoir lire les tests de publication et comprendre **qui peut publier un site, dans quel état, et ce qui se passe si une condition manque**.

## Ce que ça change quand on écrit un test

| Aspect | Ce qu’un lecteur doit pouvoir comprendre |
|---|---|
| **Nom du test** | La règle vérifiée. `test_site_without_approval_cannot_be_published` donne plus d’information que `test_publish_returns_409`. |
| **Données de départ** | Les conditions qui comptent. Ici, le site est prêt à être publié et l’utilisateur a les droits, mais l’approbation manque. |
| **Action** | Ce que l’utilisateur ou le système essaie de faire. Ici, publier le site. |
| **Assertions** | Le résultat attendu et, si c’est important pour la règle, les effets sur le système. Ici, la publication est refusée et le statut du site reste inchangé. |
| **Ensemble des tests** | Les cas qui délimitent la règle. Un site approuvé peut être publié par une personne habilitée. Un site sans approbation ne peut pas l’être, même si la personne est habilitée. |

Voici à quoi cela peut ressembler en Python avec `pytest` et des fixtures qui donnent le contexte métier.

```python
def test_site_without_approval_cannot_be_published(
    ready_site_without_approval,
    authorized_publisher,
):
    site = ready_site_without_approval

    with pytest.raises(ApprovalRequired):
        site.publish(by=authorized_publisher)

    assert site.status == SiteStatus.READY
```

La fixture `authorized_publisher` a un rôle précis. Elle établit que **les droits sont suffisants**, ce qui permet au lecteur de comprendre que le refus porte sur l’approbation. La dernière assertion exprime une deuxième garantie du même scénario. **Le refus laisse le site dans son état initial.**

## Pourquoi cette documentation est « vivante »

Si un changement casse cette règle, **le test échoue dans la CI**. Si la règle métier change volontairement, la revue de code peut examiner ensemble le changement de comportement et les exemples qui l’expriment. Un test vert confirme que le scénario écrit fonctionne. La revue reste nécessaire pour vérifier que ce scénario exprime toujours la règle voulue.

Le niveau auquel tu poses le test dépend de **ce que tu veux garantir**. Si tu documentes la règle d’approbation, le test métier ci-dessus convient. Si tu documentes le contrat d’une API publique, le code HTTP `409` et le code d’erreur retourné aux clients peuvent être des assertions pertinentes. Par exemple, un client peut s’appuyer sur ce code d’erreur pour afficher « Demander une approbation ».

**En revue, je poserais cette question** : « En lisant ce test sans ouvrir l’implémentation, est-ce que je peux expliquer la règle qu’il protège et donner un exemple concret de ce qui doit se passer ? » Si la réponse est oui, le test sert aussi de documentation.

```
Reducing redundant test bloat generated by AI coding agents

Unlike humans, coding agents love to write tests, and many of them in all shapes and colors.

They spam our codebase with repetitive tests trying to optimize for coverage as much as possible. This leads to longer CI times and more token spends when they try to read these files, in other words it increases the cost on all front.

Here’s a prompt to help you cut all the unnecessary tests. I removed 300 tests and over 5k lines of code from only two repos of daily dev.

    use dynamic workflow to identify all the redundant tests in this codebase and remove them. by redundant i mean they basically test nothing, another test already covers them and they just waste cpu time for ci. check for cross file dups as well.

To avoid future bloat, add this to your agents/claude md file:

    Same branch is not a new test: before adding a test that differs from a neighbour only in an input value, confirm the production code actually branches on that difference — a passthrough field, or one guard rejecting every disallowed enum, means the existing test already covers it.

```
